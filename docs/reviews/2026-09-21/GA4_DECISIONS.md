# GA4 implementation decisions

These decisions explain the delta from `01535f2`. [Implementation review](GA4_ENGINEERING_REVIEW.md) records evidence; [operator setup](../../integrations/google-analytics.md) records deployment requirements. The connector is implemented but disabled and has not completed real-Google acceptance.

| Decision | Reason and tradeoff |
|---|---|
| Stack GA4/security after the UI proposal PR | Keeps customer credentials/schema changes reviewable separately from the prototype. Parent PRs must land or be reconciled before this branch can merge cleanly into main. Proposal D remains a visual prototype. |
| Use the existing metric and measurement pipeline | Imported values become ordinary confirmed connector metrics, selectable by existing Core Metrics/report bindings. Reusing the pipeline preserves model behavior and avoids a second set of impact calculations. It also preserves the existing plan/exposure/history requirements. |
| Require owner/admin consent, preview and confirmation | A Google grant alone should not decide which property or metric belongs in a workspace. Core selection remains explicit after import. This adds a deliberate step before customer data becomes analysis input. |
| Begin with additive daily counts | Sessions, engaged sessions and event count have explicit sum semantics. Rates, revenue/currency conversion, daily unique users and portfolio rollups need additional contracts. A daily unique-user series cannot safely become quarterly unique users by summation. |
| Bind one property and immutable metric/filter semantics | Prevents a report's underlying meaning from changing when someone edits connector settings. Renaming a metric is allowed; changing property, timezone, event filter or beneficial direction requires a new connection/metric. Initial scope supports one event filter per connection. |
| Preserve property-local days | GA4's daily dates are not necessarily UTC days. The previous measurement path assumed UTC. Definition validation, registration deadlines and worker resume times now use the metric timezone; statistical formulas and thresholds remain unchanged. |
| Backfill 180 completed days; revisit seven days by default | Supplies historical baseline data while bounding cost and runtime. Recent Google aggregates can change. The overlap is configurable up to 180 days, and delayed runs catch up within that cap. Revisions older than the configured window require a deliberate wider refresh. |
| Keep missing days and provider quality restrictions visible | Omitted rows do not prove zero activity. A complete fetched window can therefore delete a formerly present row and leave a gap. Sampled, thresholded, restricted or other-row data is recorded as withheld; the first release prioritizes interpretable evidence over always producing a number. |
| Encrypt refresh tokens privately; use an RPC-only worker credential | Browser clients and ordinary database roles never receive token material. The worker has no direct table grants. This narrows access compared with a general service-role client, but the application runtime remains trusted and operators must manage encryption-key backup and worker-token renewal. |
| Bind OAuth to both user/workspace and initiating browser | A ten-minute single-use state hash, HttpOnly state cookie and fixed callback protect against callback substitution. An OpenID subject binds refresh-token reuse to the same Google account. Causent membership is checked independently of Google access. |
| Serialize sync and publish atomically | A five-minute lease plus connection generation prevents overlapping refresh/publish operations. Every mapped metric must validate before the transaction publishes observations, receipts and recompute requests. Failed batches leave the previous data intact; lost-response retries are harmless. |
| Invalidate locally before provider revocation | Disconnect stops collection even if Google is unavailable. Stored history remains for auditability. If remote revocation fails, the user gets a Google Account removal instruction; deleting local credentials alone cannot revoke an external grant. |
| Suppress older results immediately after input changes | Waiting for the next recompute could leave a confident result visible after its data was revised, revoked or became stale. A SQL health/receipt gate hides that result immediately; the Python loader independently checks the same input conditions. The cost is a temporary waiting state after updates. |
| Keep existing models and causal gates | A successful import does not establish rollout exposure, register a prospective plan or create causal evidence. Existing 45–180-day windows and fixed-horizon rules remain. Combined project impact, new models and BigQuery are deferred. |
| Patch vulnerable dependencies and add limited browser protections | The requested security review found affected package versions, so the PR includes runtime/editor updates and rebuilt proposal bundles. Frame/object/base/referrer protections are added. A full script-source CSP is deferred because it needs a separate nonce and application-compatibility design. |
| Separate automated evidence from release acceptance | Provider fixtures, real local role/transaction tests, browser/HTTP checks and dependency scans answer different questions. They do not prove customer Google consent, hosted settings or numerical parity with an actual property. Those remain explicit staging gates; the feature flag stays off by default. |

## Findings that changed the implementation

The first review found the UTC assumption, so timezone handling was corrected through registration and worker scheduling. Database probes then drove explicit null-lease rejection, authority checks after membership removal, and suppression of older readouts when receipt identity changes. Provider checks added acceptance of Google's empty revocation response and a total operation deadline. HTTP checks caught global security headers overriding the callback's stricter referrer setting; the callback path now has an explicit configuration override.

The dependency scan changed the package scope: Next/ESLint, Tiptap, Sharp, Undici, PostCSS and affected utilities were patched. Both packaged editors were rebuilt so the static proposals did not retain the vulnerable code. These are source fixes awaiting release, not a claim that production is already patched.

The hosted check subsequently confirmed RLS, security-invoker views and private image-bucket settings, but returned 32 privileged-RPC warnings and disabled leaked-password protection. The decision was to document the actual deployed state and require targeted review/configuration follow-through, rather than blindly revoke application permissions or change production during a PR task.

## Decisions still requiring external evidence

A consenting GA4 property must pass a date/value comparison and refresh/disconnect acceptance. Operators must verify hosted grants/API exposure, auth/Storage/CORS settings, environment separation, scheduled runtime support and key/token rotation. No release date, broad enablement or production migration is approved by this decision record.
