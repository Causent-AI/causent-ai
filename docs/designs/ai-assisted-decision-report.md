### Slice 10 boundary: explicit report iterations

The system already supports multiple independent reports and append-only revisions while a report
is editable. “Multiple iterations” therefore means a richer, post-activation workflow: an active
report may create an explicit successor report in the same linear series. It does not mean unlocking
or silently appending to the active report.

Each series has one explicit current active report. Starting the next iteration is a checked,
idempotent transition from that active parent to one draft successor, seeded from the exact activated
snapshot and accompanied by a required iteration reason. Unchanged logical claims and draft-action
source IDs remain stable for comparison, while the successor receives new report/revision identities.
The seed strips `implementation.assetIds`: assets and Storage paths are report-bound, so a user must
explicitly reattach a sanitized image rather than reusing private object identity across reports.

The parent stays the operational report while the successor is edited. Successor activation creates
new canonical decision, prediction, and action rows through the existing atomic boundary, then moves
the series current pointer in that same transaction. Prior canonical and audit rows never change.
Actions & Decisions, Data Workshop, and Impact select the explicit series pointer rather than relying
on `updated_at` ordering; Reports groups and links every non-deleted iteration. A removed draft leaves
the pointer alone. Removing the current successor selects only the nearest non-deleted active
predecessor in that series, or no current report when none exists.

The first implementation is deliberately linear: no branches or merges, in-place active edits,
automatic action cancellation, cross-report asset reuse, historical graph rewriting, revision
diff/restore/export UI, or model-driven regeneration. It must pass three sequential iteration cycles,
stale/idempotent retry cases, RLS isolation, rollback/removal cases, and current-project browser
acceptance. The user explicitly overrode the normal Slice 9 implementation gate for this run. That
product-direction decision allowed implementation; it did not supply or pass the missing partner evidence.

### Implemented Slice 10 contract — 2026-07-23

The prepared boundary is implemented as a database-owned linear series. Existing reports are
backfilled into one-report series. A checked successor operation locks current series and parent,
reuses exact retries, rejects changed/stale requests, preserves logical claim/action source IDs, and
removes `implementation.assetIds` before revision 1. The existing activation path advances the pointer
inside the canonical materialization transaction. Deletion moves a current pointer only to the nearest
non-deleted active predecessor in the same series.

Reports groups iterations and exposes **Start next iteration** only on a current active report. Actions
& Decisions, Data Workshop, and Impact select the explicit pointer rather than timestamps. This was
implemented under an explicit product-direction override, not evidence that the Slice 9 release gate passed.

### Implemented expanded MVP sources and provenance v2 — 2026-07-23

Generation accepts the bounded project brief plus at most one public HTTPS page and one text-based
PDF. URL retrieval requires HTTPS on port 443, rejects credentials and private/non-public DNS results,
pins the validated address, revalidates up to three redirects, accepts only UTF-8 HTML/plain text,
and enforces a 1 MiB response and 10-second total timeout. It retains only a sanitized origin/path
locator, never cookies, credentials, query strings, fragments, or response bytes.

PDF extraction accepts one file up to 5 MiB and 40 pages. A resource-limited worker has a 12-second
deadline and rejects invalid signatures, encryption, active content, embedded files, malformed PDFs,
and sources without readable text. This is text extraction only: scanned documents require OCR before
upload, and OCR is not part of the MVP. Each extracted source is capped at 48,000 characters; the
combined brief/source corpus is capped at 72,000 characters and split into chunks of at most 2,000.

Every newly generated or edited report is schema version 2. Its RLS-protected revision snapshot stores
bounded source summaries, chunk text and locators, per-chunk and per-source SHA-256 digests, and explicit
claim-to-chunk IDs. Database validation recomputes the digests and rejects a `sourced` claim whose chunk
does not exist. Historical v1 snapshots remain readable; a legacy-derived successor must be saved once
as v2 before activation.

### Implemented automatic current-report causal recomputation — 2026-07-23

Activation v2 requires one selected action as the primary manual lever. Activation, current-report
metric observation inserts/updates, and primary-action completion enqueue a private job keyed by the
immutable activation. Enqueues advance a requested generation and coalesce reasons; the source write
stays committed even when the immediate worker wake-up fails, because the authenticated five-minute
cron drains the same queue.

The stateful worker locks report, series, workspace, and activation, then rechecks that the activation
is still the explicit current report before reading or writing graph state. Superseded work is recorded
without mutating historical graphs. A stable input hash makes unchanged retries no-ops; failures use
bounded retries and backoff. BH-FDR still uses the complete eligible workspace hypothesis family, while
only the current activation's selected action/metric graph is persisted. The 45-day-per-side causal
confidence floor and preliminary descriptive labeling are unchanged.

### Implemented MVP completion contracts — 2026-07-23

Onboarding is blank-first. The brief, URL, and PDF fields do not inherit a fixture; Gummy Alpha and
Northstar Support appear only as explicit sample-report actions. Generation copy states that clicking
the button authorizes sending the challenge description and extracted URL/PDF text to the configured AI provider.
No generation request is sent until the bounded brief is valid and the user clicks. Provider or
transport failure leaves the user's inputs available and returns an editable fallback or actionable
retry state.

Decision Report lifecycle telemetry is best-effort and never blocks generation, saving, or
activation. It records the landed, generation-started, editable, generation-failed, saved,
save-failed, activated, and activation-failed transitions against a server-minted opaque session
key. The only allowed metadata is elapsed time; bounded numeric edit, focused-answer, and remaining-
gap counts; and booleans indicating URL/PDF use, fallback, or exact-retry reuse. Report text, prompts,
source text/locators, report and canonical identities, receipt or asset data, raw observations,
clipboard packets, and error strings are excluded. Aggregation is by distinct session and reports
stage counts/drop-off, median time to editable/save/activation, median edit/focused-answer counts,
and failure-event plus affected-session counts. No partner pass/fail threshold is inferred from
engineering telemetry. Authenticated database privileges are explicitly limited to `SELECT` and
`INSERT`; `UPDATE`, `DELETE`, and `TRUNCATE` remain revoked so RLS is not asked to enforce a
table-wide operation such as `TRUNCATE`.

Activation requires a prediction resolution date strictly later than the current UTC date at three
layers: the date input starts at tomorrow, the shared runtime validator rejects today/past/invalid
dates, and an append-only activation trigger independently checks the database statement date.
This closes stale-tab and forged-request paths without making the AI choose a date for the user.

Data Workshop and Impact display only a sanitized state for the explicit current report's automatic
recompute: `idle`, `queued`, `retrying`, `failed`, or `current`, plus the relevant request/processed
timestamp. The viewer-scoped RPC re-resolves workspace → current series → current active report →
activation, uses one non-enumerating denial for missing and unauthorized scopes, and never exposes
the private job row, attempts, error code, input hash, actor, activation/report identities, or raw
reason. Queued, retrying, and failed states preserve the last visible causal readouts.

Recovery boundaries are explicit. Generation failures retain the entered sources; inline save and
activation failures say that no partial durable plan was created; and route-level boundaries for the
app, onboarding, and Data Workshop state which saved data was not changed while offering retry and a
safe route back to Reports/onboarding. These boundaries do not suppress authorization failures or
substitute fixture data when a report-native database read fails.

Production release configuration now fails closed. The app requires an HTTPS Supabase URL, anon key,
and server-only `SUPABASE_SERVICE_ROLE_KEY`; the latter is mandatory because the first-save source
receipt can be minted only by the trusted generation path. Release checks additionally require the
app recompute URL/secret and cron secret, plus the worker's Postgres `DATABASE_URL` and matching
recompute secret. Demo, seed, fixture, and local-rollout flags must be absent in production. Invalid
configuration returns a no-store `503` and logs only variable names and issue codes, never values.
Node is pinned to `22.23.0`; the CI workflow pins Python 3.12 and Supabase CLI 2.98.1 and runs the
clean-reset app/database/engine/recompute/build gates. A hosted CI result for this working tree is
still required before release.

The shared dashboard layout is request-bound with `dynamic = "force-dynamic"`. This prevents a
production build from freezing a seed or pre-activation snapshot into workspace/current-report
surfaces. A post-build manifest guard asserts that Actions, Data Workshop, Impact, and Reports exist
and are not prerendered; it passes locally and is wired immediately after the webpack build in CI.
The Next.js 16.2.11 build classifies those routes plus onboarding as dynamic.

Completion browser acceptance started from blank onboarding, explicitly loaded the Gummy example,
confirmed provider egress, and generated/saved/activated Iteration 1. It then created and activated
three sequential successors through Iteration 4 with `+12%`, `+14%`, and `+16%` predictions. Each
predecessor remained current until successor activation; Reports showed four iterations with the
fourth current; the original direct link remained activated, read-only, and reachable; and Actions &
Decisions, Data Workshop, and Impact showed only the current report. Data Workshop and Impact showed
the sanitized `queued` recompute state, Impact retained the honest no-evidence readout, legacy-flow

## Problem Statement

Causent's current onboarding asks users to move through discrete form-like steps before they see the value of the system. The proposed experience should make the multiplicative effect of AI visible from the first prompt: a user describes what they are building, the evidence behind it, and the resources available; Causent immediately renders a partial, editable Decision Report and asks only the follow-up questions needed to make it useful.

The user remains the author and approver. AI extracts, structures, drafts, and connects work, but does not invent facts, customer evidence, metric observations, owners, expected lift, or completion probability.

## Demand Evidence

This is currently a product thesis, not validated customer demand. The first goal is a tight, production-shaped design-partner test. Success must be measured through observed use, not positive reactions to a guided demo.

## Original Status Quo (2026-07-21)

The current Causent onboarding funnel is `paste -> editable card -> prediction commitment -> lever/watch`. It already structures pasted intent, asks mechanism questions, declares or reuses a metric, commits a decision and prediction, and transitions into lever creation. Reports are rendered from dashboard data but are seed-only on the database path. The current experience exposes several separate forms before showing a complete decision artifact.

## Target User and Narrowest Wedge

The initial user is a product or business leader starting a project who can review a decision package but does not want to manually assemble it across documents, analytics, mock-ups, and ticket systems.

The narrowest production-shaped wedge is one onboarding path:

1. Enter one prompt with optional bounded sources.
2. Receive a partially complete three-section Decision Report plus its derived assets.
3. Answer focused inline questions for missing required information while editing any field directly.
4. Approve the report progressively, even when optional fields remain visibly incomplete.
5. Confirm or add a core metric.
6. Review up to 25 draft actions and select one to three for activation.

## Product Principle

**The user is still in charge; AI multiplies their work.** Each meaningful user action should create several visible, inspectable outputs in text and visualization form. Multiplication must remain reversible and attributable.

One initial prompt visibly produces multiple coordinated assets:

1. The partial three-section Decision Report
2. A sourced-evidence summary with provenance states
3. A core-metric hypothesis plus an existing-metric chart when data is available
4. An Action Plan summary and up to 25 editable draft actions
5. An optional rendered user-supplied chart or graph

These are typed views of one report aggregate, not separate free-form generations. Editing the underlying field updates every dependent view.

## Decision Report Structure

### 1. Decision

- One readable paragraph composed of editable Background, Problem, and Decision claims
- Visible highlighting and direct editing for any required claim that remains missing

### 2. Supporting Evidence

- One editable evidence paragraph; supplied proof remains traceable to its source
- One optional sanitized private chart or graph
- Core Metrics selection below the evidence

### 3. Implementation

- Action Plan summary at the top
- Up to 25 editable draft actions; one to three may be confirmed for activation
- Customers and stakeholders with one optional indicator
- Owners
- Optional action metadata

The reasoning spine is:

1. What is the decision?
2. What factors led to this decision?

These questions guide generation and follow-up; they are not additional top-level sections.

## Premises

1. The first prompt streams a partially completed, editable Decision Report rather than returning a prose answer.
2. Every atomic claim has a status: `sourced`, `inferred`, `suggested`, `missing`, or `user_confirmed`. A field may derive a summary status for display, but provenance belongs to claims, not the whole field.
3. The editable report remains the sole autosaved draft during onboarding. One final idempotent activation step materializes the canonical decision, metric relationship, prediction commitment, and selected actions so they cannot become disconnected copies.
4. Report readiness requires Background, Problem, Decision, an Action Plan summary, and at least one proposed action. Supporting evidence, metric rationale, and optional Implementation context may remain visibly missing. Final activation separately requires a confirmed metric relationship, the human prediction commitment, and one to three approved actions.
5. The first-run experience presents Decision Report -> metric confirmation or Data Workshop -> Action Plan as a clear sequence. It may use sections or explicit links rather than forced conversational navigation.
6. Impact is introduced as the destination for future measurement but is not forced before evidence exists.
7. The expanded MVP accepts the initial prompt, pasted supporting text, one bounded public HTTPS page, one bounded text-based PDF, existing Causent metrics or one metric CSV, and one supplied PNG/JPEG chart or graph. It does not crawl links, authenticate to pages, or perform OCR.
8. User-supplied charts or graphs render through the existing report-bound private-image path. Original chart generation and a multi-asset builder are deferred.
9. `Completion Outlook` appears only behind the design-partner feature flag as a clearly labeled concept. No unexplained numeric probability is shown and it is not part of MVP success measurement.
10. Execution governance belongs at the action level. Legacy report-snapshot declarations remain readable for compatibility, but Review #2 removes the report-level governance editor; broader automated enforcement is deferred.

## Lifecycle and Approval Semantics

The partner wedge uses one draft and one canonical write boundary:

```text
draft -> report_ready -- explicit atomic activation --> active
              |
              \-- validation/write failure --> report_ready (retry safely)
```

- `draft`: generation, inline gap questions, and direct report edits autosave as serialized append-only report revisions.
- `report_ready`: Background, Problem, Decision, the Action Plan summary, and at least one of up to 25 draft actions pass deterministic validation. Supporting evidence, metric rationale, and optional Implementation fields may remain missing.
- `activation_ready` is derived UI readiness, not a persisted report status: a confirmed metric, the human-entered prediction, and one to three selected actions target the exact reviewed revision and pass deterministic validation.
- Materialization is one database transaction. It either creates the decision, prediction, actions, links, and activation audit together or creates none of them.
- On validation, authorization, or write failure, the complete `report_ready` revision remains intact. An identical retry is safe; changed input after activation is rejected.
- `active`: canonical IDs are stored on the report and the first-run experience will not repeat.

An active report is immutable. New intent may start an independent report, while **Start next iteration** creates one explicit successor in the same linear series. The active parent remains operational until successor activation atomically creates a new canonical graph and advances the current pointer. Silent canonical mutation is never allowed.

## Trust and Provenance Contract

The AI may:

- Extract claims and entities from supplied material.
- Summarize evidence.
- Draft qualitative report fields.
- Suggest actions.
- Suggest a core metric to measure without presenting causal rationale as supplied evidence.

The AI may not silently invent:

- Customers, quotes, or research findings
- Metric observations or historical performance
- Owners or stakeholders
- Dates
- Expected lift or prediction magnitude
- Completion probability

Each atomic claim stores zero or more explicit source references in Causent's schema. `suggested` content is hypothetical and renders outside the evidence presentation until a user confirms it. Anthropic strict structured output and native interleaved citations are incompatible, so provenance should be represented as Causent source-chunk IDs and excerpts rather than relying on provider-specific citation blocks.

## Guided Assistance Design

The partner wedge does not require a general chatbot or persisted conversation. Assistance is embedded into the report:

- The initial prompt generates the partial report and its derived assets.
- A deterministic gap scanner ranks required missing fields.
- The UI renders focused questions beside or beneath the relevant field.
- The model may phrase a question and propose a typed field update, but application code controls what is asked and what may change.
- Direct editing and answering a question use the same validated server commands.
- The UI explains source status, why a metric is required, and what remains before approval.
- Model failure leaves the partial report fully editable and falls back to deterministic question copy.

This preserves a production path to conversational delivery later: the report schema, gap scanner, typed commands, generation service, and provenance remain reusable. A future chat interface becomes another client of those contracts rather than a replacement.

Estimated guided-assistance work: 4-7 implementation days, overlapping report UI and generation:

- 2-3 days: typed generation, section events, validation, and deterministic fallback
- 1-2 days: gap scanner, inline questions, and typed updates
- 1-2 days: provenance guards, timeout/refusal handling, and adversarial tests

## Canonical Data Model

Add a durable report aggregate rather than storing the document only in client state:

- `decision_reports`: identity, scope, lifecycle state, active revision, onboarding progress
- `decision_report_revisions`: append-only structured snapshots or patches, author type, timestamp
- `decision_report_activations`: append-only activation inputs, input hash, canonical identities, actor, and timestamp
- `sourceSummaries` in schema-v2 `decision_report_revisions`: bounded brief/URL/PDF chunks,
  sanitized locators, retrieval metadata, and cryptographic provenance. No raw URL/PDF source table
  or source-byte retention is introduced.
- `report_assets`: Supabase Storage references for the one sanitized user-supplied image

Revisions use append-only full JSON snapshots in the MVP. Patches are request/response transport only and contain `report_id`, `base_revision_id`, permitted field operations, and the proposed new claim values. The server rejects stale base revisions with a conflict response and returns the current revision for user reconciliation.

The structured report should have one versioned typed schema shared by model validation, server actions, persistence, and rendering. A starting contract is:

```ts
type ClaimStatus = "sourced" | "inferred" | "suggested" | "missing" | "user_confirmed";

type Claim = {
  id: string;
  text: string;
  status: ClaimStatus;
  sourceChunkIds: string[];
};

type DraftAction = {
  sourceItemId: string;
  title: string;
  summary: Claim[];
  owner: Claim | null;
};

type DecisionReportV1 = {
  schemaVersion: 1 | 2; // v1 readable history; newly generated/edited reports are v2
  decision: { decision: Claim[]; background: Claim[]; problem: Claim[] };
  supportingEvidence: {
    factors: Claim[];
    metricMechanism: Claim[];
  };
  implementation: {
    actionPlanSummary: Claim[];
    actions: DraftAction[]; // 1..3 at report approval
    customers: Claim[];
    stakeholders: Claim[];
    assetIds: string[];
    governance: {
      dataClassification: "private" | "organization" | "public" | null;
      allowedDataSources: Claim[];
      approvedModelNotes: Claim[];
    };
  };
  sourceSummaries?: ReportSourceSummary[]; // required and digest-validated for v2
};
```

`dataClassification` is descriptive metadata only and never changes authorization or Storage visibility. Actual access remains scope/RLS controlled and private by default.

Runtime schema rules, not TypeScript comments, enforce cardinality and transition requirements. The untrusted model DTO uses `null` for an unknown scalar claim and `[]` for an unknown claim list; server materialization creates `Claim { status: "missing" }` only for a field the UI must visibly request. At `report_ready`, Background, Problem, Decision, Action Plan summary, and at least one of up to 25 draft actions must be present. Supporting evidence and metric rationale are optional. At `activation_ready`, the reviewed revision, confirmed metric, human prediction commitment, and one to three selected action source-item IDs are required. At `active`, the canonical decision, prediction, and at least one approved action ID are required.

Before parallel implementation begins, this contract and one complete golden JSON fixture must pass shared contract tests.

Model output never supplies trusted IDs. The server assigns immutable claim IDs and action source-item IDs when accepting a completed section. Regeneration preserves IDs only when the server deterministically matches the same logical schema path; new list entries get new IDs.

The MVP patch protocol is server-owned and versioned:

```ts
type ReportPatchV1 = {
  schemaVersion: 1;
  reportId: string;
  baseRevisionId: string;
  operations: Array<
    | { op: "replace_claim_text"; claimId: string; text: string }
    | { op: "confirm_claim"; claimId: string }
    | { op: "add_list_claim"; path: string; afterClaimId: string | null; text: string }
    | { op: "delete_list_claim"; claimId: string }
    | { op: "move_list_claim"; claimId: string; afterClaimId: string | null }
    | { op: "set_action_title"; sourceItemId: string; title: string }
    | { op: "set_action_owner"; sourceItemId: string; text: string | null }
    | { op: "add_action"; afterSourceItemId: string | null; title: string }
    | { op: "delete_action"; sourceItemId: string }
    | { op: "move_action"; sourceItemId: string; afterSourceItemId: string | null }
    | { op: "attach_asset"; assetId: string }
    | { op: "detach_asset"; assetId: string }
    | { op: "set_data_classification"; value: "private" | "organization" | "public" | null }
  >;
};
```

Clients cannot patch source IDs or set `sourced` status directly. Model proposals use the same server commands but remain `suggested` or `inferred` until provenance validation or user confirmation. For the first sourced save, generation mints a private 24-hour, one-use receipt bound to the actor, scope, exact source summaries, and sourced-claim multiset. The checked save consumes it atomically; an exact lost-ack retry reuses the committed result and a changed replay conflicts. The server also validates paths, permissions, cardinality, asset ownership/scan status, and revision freshness, then produces a new full snapshot. A stale base revision returns `409` with the current revision ID and no partial application.

Status-dependent runtime invariants are mandatory: `sourced` requires at least one existing, authorized source chunk; `user_confirmed` records the confirming user and revision; `missing` has no text or source; `suggested` is never counted as evidence. Later revisions freeze the authorized source corpus and may only retain or remove previously authorized sourced claims. Authenticated callers cannot mint a receipt or promote even a consistently rehashed forged corpus. A source-free report with no sourced claims has no provenance authority to mint and needs no receipt. Soft-deleted reports retain their append-only revision provenance for audit while authenticated reads fail closed.

Materialization is one idempotent orchestration over existing write paths. Every created row keeps its originating report, revision, and source-item ID. Exact graph:

```text
decision_report --approved revision--> decision
decision --decision_actions--> action (1..3, after action approval)
decision --human commitment--> prediction --confirmed metric--> metric
activation --selected primary action--> manual lever
```

Activation v2 creates the one primary manual lever needed for automatic recomputation. External
tracker connection and provider attribution remain subsequent explicit steps.

Avoid introducing a general block-editor schema in this MVP. The three report sections and their field types are prescribed and should render through purpose-built React components.

## Partner Input Security Boundary

- Text input is length-capped, treated as untrusted evidence, and can never change system instructions, tools, policies, or allowed output paths.
- The supplied chart or graph is limited to one size-capped PNG/JPEG. The server verifies magic bytes, decodes it, and re-encodes it into a clean image before private Storage persistence.
- One URL may fetch only public HTTPS HTML/plain text through DNS/IP validation, address pinning,
  redirect revalidation, byte/time limits, and no credentials or cookies. One text PDF may be parsed
  inside a time- and memory-limited worker; active content, encryption, embedded files, and OCR are rejected.
- Source records have explicit retention and deletion behavior. The delivered soft delete revokes authenticated report/revision/asset access immediately while retaining private bytes and audit metadata for recoverable cleanup; physical unshared-object garbage collection is deferred. Canonical graph history remains explainable without resurfacing a removed report in workspace views.
- Every persisted source summary and chunk lives inside the tenant-scoped, RLS-protected revision
  snapshot. Provenance v2 stores bounded extracted text and digests, not raw URL responses or PDFs.
- Source authority is conveyed only by the private one-use receipt described above. The receipt ID is
  transient client state and never enters the revision snapshot.

### Supplied-image contract implemented in Slice 8 (2026-07-22)

The MVP accepts one image only after the report has a durable current revision. Input is capped at
5 MiB, 4096 pixels per axis, and 16 megapixels. The server verifies PNG/JPEG signatures and exact
file boundaries, fully decodes the image with a pixel limit, rejects animation and unsupported
color spaces, normalizes orientation/colorspace, and deterministically re-encodes PNG or JPEG.
EXIF, GPS, comments, ICC/profile surprises, original filenames, and original bytes are not retained.

Only the derivative is written to the private `decision-report-assets` bucket. `report_assets`
binds its unguessable server-owned path to the workspace, report, reservation revision, attachment
revision, dimensions, media type, byte size, and SHA-256 hash. Checked RPCs reserve and attach or
detach against the locked current editable revision. A revision trigger prevents the ordinary save
path from promoting arbitrary asset IDs. Authenticated preview bytes are served through a scoped
route; bucket/path details remain server-only. Member access is required for asset reads and
mutations, and `dataClassification` never changes this policy.

Replacement commits the new asset/revision before retiring the previous object. Removal commits a
new no-asset revision before deleting the object. If Storage cleanup fails, detached metadata stays
as a cleanup marker; metadata is deleted only after Storage confirms removal. Active reports retain
their private preview but expose no replace/remove controls. Originals, multiple/shared assets,
generated images, public access, and background media pipelines remain outside the partner wedge.
The bounded URL/PDF source path is separate from private image Storage and never reuses an image
asset ID or object path in a successor.

## Failure and Recovery Contract

| Failure | Preserved state | User control |
|---|---|---|
| Provider-egress confirmation is absent or stale | Blank/entered brief and sources; no provider request | Review the disclosure and confirm after the final source edit |
| Model timeout before a section | Last complete revision and initial input | Retry missing section or edit manually |
| Malformed/invalid section | Last valid revision; rejected output logged without source content | Retry once, then deterministic empty section |
| URL rejected, timed out, redirected unsafely, or exceeded limits | Brief and other valid input; no response bytes persisted | Fix/remove the URL and generate again |
| PDF malformed, unsafe, scanned, timed out, or exceeded limits | Brief and other valid input; no PDF bytes persisted | Upload a smaller text-based PDF or continue without it |
| Image decode/re-encode failure | Existing draft plus failed asset status | Replace image or continue without it |
| Stale edit conflict | Both base and current revision IDs | Review conflict and reapply selected edits |
| Materialization failure | Exact approved revision; canonical graph unchanged | Retry the same atomic activation |
| Recompute queued, retrying, or exhausted | Existing causal readouts and immutable source/activation rows | Wait for automatic retry or ask an operator to inspect the worker; no historical rewrite |
| App, onboarding, or Data Workshop render failure | Saved reports/revisions or metric observations are unchanged | Retry the route or return to Reports/onboarding |
| Navigation interruption | Persisted lifecycle and guide state | Resume exact incomplete transition |
| Clipboard unavailable or external review invalid/stale | Current Causent report and graph remain unchanged | Select the visible packet manually or paste a fresh bounded review |

## Primary Bottleneck

The largest bottleneck is not token metering. It is integrated product acceptance:

- Does the report feel immediately useful rather than like an AI-filled form?
- Are unsupported claims visibly differentiated from sourced claims?
- Does approval create the correct canonical records exactly once?
- Does the one-time guided journey survive refresh, Back, partial uploads, and model failures?
- Are generated actions specific enough to use but not falsely authoritative?

The founder's review is required at a few high-leverage checkpoints, not on every code change:

1. Approve the typed report schema and one realistic fixture.
2. Approve the interaction after watching the first end-to-end prototype.
3. Validate report logic and action quality on 5-10 adversarial scenarios.
4. Approve the production journey after a clean-account test.

Token cost should be instrumented, but it is unlikely to control schedule. Start with one provider and one production model plus observability. Introduce cheaper extraction models, caching, or routing only after measured cost or latency justifies them. Regenerate only affected fields rather than the whole report.
